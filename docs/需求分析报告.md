## 1. 项目概述

### 1.1 背景与动机

科学上网场景中，机场（订阅服务商）提供的订阅链接格式五花八门：有的是 Base64 编码的单链接列表，有的是 Clash YAML 完整配置，有的甚至只给 SS/VMess 单节点链接。而客户端（OpenClash / Mihomo / Clash Verge / Surge / Quantumult X 等）各自要求的配置格式不同。**订阅转换（Subscription Converter）** 的作用就是：拉取原始订阅 → 解析节点 → 按目标客户端模板重新组装（节点过滤/重命名、策略组构建、规则注入）→ 输出目标格式的订阅链接。

用户当前使用 OpenClash（ImmortalWrt 路由器 192.168.10.1），订阅被聚合为「订阅聚合.yaml」，节点名形如 `🇯🇵 AWS日本01 | 电信移动联通推荐`。用户存在一个**刚性约束**：OpenClash 自定义规则文件（`/etc/openclash/custom/openclash_custom_rules.list`）中的策略目标必须与订阅中的策略组名/节点名**逐字符精确匹配**（含 emoji、空格、`|` 分隔符）。公共订阅转换服务（或机场原生订阅）生成的组名/节点名不可控，导致自定义规则频繁失效、需要手工改规则——这是本项目最直接的痛点来源。

### 1.2 项目目标

构建一个**自托管、全容器化（Docker Compose）、面向 OpenClash 深度定制**的订阅转换服务：

1. **核心目标**：把任意来源的订阅（多机场聚合、单节点链接）转换为 OpenClash/Mihomo 可直接消费的 Clash YAML 订阅，且**节点名、策略组名完全可控**（与用户自定义规则精确对齐）。
2. **安全目标**：订阅 URL 含机场凭证，自托管避免节点信息经第三方转换服务泄露；不依赖公共转换服务的稳定性。
3. **运维目标**：部署在 NAS（192.168.10.10）Docker 环境，内存占用必须适配 NAS 仅 3.8Gi 的约束；配置持久化、一键更新、故障可排查。

### 1.3 目标用户

- 主要用户：阳羽本人（家庭网络管理员，OpenClash 深度用户）。
- 潜在用户：家庭内其他需要 Clash 系订阅的设备。
- 不面向公网多用户（自用优先，鉴权留接口）。

## 2. 领域调研

### 2.1 订阅转换的核心流程

```
原始订阅(URL/文件) ──拉取──▶ 解析节点 ──过滤/重命名──▶ 节点列表
                                                        │
用户模板(规则/策略组/DNS) ──合并──▶ 生成目标格式 YAML ──▶ 输出订阅链接
```

关键认知：

1. **转换后端是核心，前端只是 URL 拼接器**（subconverter 生态的共识）。真正起作用的是后端服务。
2. **转换链路每次更新订阅都会执行**：OpenClash 定时更新订阅 → 访问转换 URL → 后端现场拉取原始订阅并转换 → 返回 YAML → OpenClash 应用。因此转换服务必须常驻运行。
3. **两种技术路线**（详见 3.2）：
   - **传统路线**（subconverter）：后端拉取订阅 → 解析节点 → 回写节点参数 → 输出完整配置。后端需要持续维护协议解析能力。
   - **现代路线**（SubConverter-Extended）：后端不拉取远程订阅，直接在输出配置中生成 `proxy-providers` 字段，由 Mihomo 内核自己拉取订阅。架构上规避了「订阅源访问受限」和「协议支持滞后」两类问题。

### 2.2 代理协议全景（2026-08 现状）

转换工具需要支持的输入/输出协议：

| 协议 | 链接格式 | Mihomo 支持 | 备注 |
|------|---------|:---:|------|
| Shadowsocks | `ss://` (SIP002 Base64) | ✅ | 经典协议，chacha20 等加密已被社区弃用 |
| ShadowsocksR | `ssr://` Base64 | ✅(兼容) | 老协议，魔改内核支持 |
| VMess | `vmess://` Base64(JSON) | ✅ | V2Ray 系，含 ws/grpc/tcp 传输、TLS |
| VLESS | `vless://uuid@host:port?params` | ✅ | 含 Reality 支持 |
| Trojan | `trojan://pass@host:port?params` | ✅ | 含 Trojan-Go/WS |
| Hysteria / Hysteria2 | `hy2://` / `hysteria://` | ✅ | 基于 QUIC，机场常用新协议 |
| TUIC | `tuic://` | ✅ | 基于 QUIC v5 |
| AnyTLS | `anytls://` | ✅ | 新协议（subconverter 2026-07 刚加支持） |
| WireGuard | `wireguard://` | ✅ | 视后端/客户端支持 |
| Snell | `snell://` | ✅ | Surge 系 |
| Socks5 / HTTP | `socks5://` / `http://` | ✅ | 直连代理，无加密 |
| Mieru 等小众协议 | — | 视支持 | 依赖后端与客户端 |

> 结论：协议清单是**动态演进的**。2026 年机场主流是 VLESS+Reality、Hysteria2、TUIC、AnyTLS、Trojan。设计上必须把「协议解析层」与「业务层」解耦，并考虑复用 Mihomo 内核解析器（SubConverter-Extended 的做法）或持续跟踪上游。

### 2.3 Clash / Mihomo 配置结构（输出格式核心）

转换目标产物是 Clash YAML（OpenClash 直接消费）。核心字段：

```yaml
mixed-port: 7893            # 混合端口
dns:                        # DNS 配置（nameserver/fallback/fake-ip/nameserver-policy）
proxies:                    # 节点列表（每协议字段不同）
proxy-groups:               # 策略组：select / url-test / fallback / load-balance
  - name: 🚀 节点选择
    type: select
    proxies: [自动选择, 香港节点, ...]
proxy-providers:            # 可选：远程订阅提供器（内核自行拉取）
  - type: http
    url: <机场订阅链接>
    interval: 43200
    health-check: {enable: true, interval: 300, url: ...}
rules:                      # 分流规则（DOMAIN / DOMAIN-SUFFIX / DOMAIN-KEYWORD /
                            #   IP-CIDR / GEOIP / GEOSITE / MATCH ...）
rule-providers:             # 可选：远程规则集（http 拉取，定时更新）
```

与 OpenClash 集成的关键点：

1. **节点名/组名就是「契约」**：自定义规则文件的 policy 目标必须与 `proxies`/`proxy-groups` 中的 name **逐字符一致**（用户铁律：emoji、空格、`|` 一个不能差）。
2. **规则组类型**：url-test（自动选最快）、fallback（按序回退）、select（手动）、load-balance（负载均衡）。用户场景需要「按地区分组 + 组内自动选优」。
3. **rule-providers 是规则维护的现代方式**：规则集走 HTTP 拉取、定时更新，转换服务只需在输出中引用规则集 URL，规则本体的增删改不依赖重新转换。
4. **proxy-providers 是「免转换」方案**：Mihomo 内核原生支持直接订阅远程链接并定期同步，配合 health-check 自动测活。这改变了转换工具的角色——从「搬运节点」变成「生成引用」。
5. **DNS 段**：OpenClash 有 overwrite 机制（UCI 是源真相），转换输出中的 DNS 段会被 OpenClash 覆写设置覆盖。模板中 DNS 段应给出合理默认，但不要假设它是最终生效值。

### 2.4 订阅输入格式

| 格式 | 形态 | 解析难度 |
|------|------|---------|
| Base64 单链接列表 | 每行一个节点链接（ss/ssr/vmess/vless/trojan/hy2…） | 低 |
| Clash YAML（proxies 或完整配置） | YAML | 中（需 YAML 解析 + 字段映射） |
| SIP008（SS 软件订阅） | JSON | 低 |
| SSD | JSON | 中 |
| Surge / Quantumult X 配置 | 分段文本 | 中 |
| 混合（订阅内含其他订阅引用） | 递归 | 高 |

### 2.5 OpenClash 对接方式（消费侧）

OpenClash 消费转换服务的三种典型姿势：

1. **配置订阅 URL 直填转换链接**（最常用）：
   ```
   http://192.168.10.10:25500/sub?target=clash&url=<URL编码的机场订阅>&config=<URL编码的模板地址>
   ```
   在 OpenClash「配置订阅」添加该 URL，定时更新。规则与节点每次更新都重新转换。
2. **OpenClash 内置订阅转换**：新版 OpenClash 自带「订阅转换」能力（在线转换开关 + 后端地址 + 内置模板列表，如 Aethersailor/Custom_OpenClash_Rules 的模板已被官方收录）。自建服务可平替这里的后端地址。
3. **远程 YAML 覆写模块**：OpenClash 支持远程覆写（overwrite），把自定义规则/策略组以覆写模块方式挂载，订阅更新后自动应用——与转换服务互补而非互斥。

### 2.6 订阅源访问限制（重要约束）

机场订阅常见限制：
- **User-Agent 限制**：订阅接口校验 UA，转换后端必须能自定义/伪装 UA。
- **地区/来源限制**：部分机场订阅接口限制来源 IP（如仅允许机场所在地区访问），或订阅本身被墙。此时传统后端（部署在国内 NAS）拉取失败。
- 对策：a) 后端部署在国外 VPS（本项目不适用，NAS 在国内）；b) 走代理拉取（转换服务出站走 OpenClash 显式代理端口 7893）；c) **proxy-provider 方案**（把拉取责任转移给 Mihomo 内核，内核可用代理拉订阅——SubConverter-Extended 的架构优势）；d) UA 伪装 + 重试。

## 3. 竞品分析

### 3.1 tindy2013/subconverter（事实标准，17k★）

- **定位**：通用订阅格式转换后端（C++，单二进制，内存占用 ~20MB）。
- **能力**：15+ 输入格式 → 15+ 输出格式；`include`/`exclude` 正则过滤节点；`rename` 正则重命名；外部 `.ini` 模板（自定义策略组 + 规则）；多订阅 `|` 合并；`&upload=true` 自动同步 Gist；自定义 UA。
- **模板生态**：ACL4SSR（最流行的规则模板）、各种 OpenClash 定制模板均基于其模板体系。
- **缺点**：无 Web UI（需配 sub-web 前端）；协议解析靠人工维护，新协议支持滞后；后端拉取订阅 → 订阅源访问限制问题无法从架构规避；代码库 C++ 较老，二次开发门槛高。
- **Docker 部署**：`tindy2013/subconverter` 官方镜像，端口 25500，挂载 `/mnt` 存配置。

### 3.2 Aethersailor/SubConverter-Extended（890★，2026 活跃）

- **定位**：subconverter 的 Mihomo 专用增强版。
- **核心创新**：目标客户端为 Mihomo 系时，输出**直接生成 `proxy-providers` 字段**，后端不拉取远程订阅 → 规避订阅源访问限制 + 协议支持滞后（跟随 Mihomo 内核解析能力，内置 Mihomo 解析器模块）；兼容原版模板；提供可视化仪表盘。
- **OpenClash 生态绑定**：作者同时维护 Custom_OpenClash_Rules（其订阅转换模板已收录进 OpenClash 内置模板列表）。
- **缺点**：深度绑定 Mihomo 系客户端；比原版复杂；同样 C++ 为主。

### 3.3 Sub-Store（订阅管理器）

- **定位**：高级订阅管理器（订阅汇总/存储/同步/转换/节点操作/脚本操作/测速/落地检测）。
- **形态**：Node.js 后端 + Web 前端，可 Docker 部署，也可作为 Surge/QX/Loon 模块运行。
- **优点**：节点操作（过滤/重命名/去重/排序）可视化、脚本化覆写能力强、多客户端适配。
- **缺点**：面向「管理多设备多客户端」场景，对 OpenClash 单点深度定制（精确命名契约）不如自建模板直接；上手曲线陡。

### 3.4 sub-web / ACL4SSR 前端

- 纯前端（Vue），作用是拼接后端 URL + 可视化选择参数，不参与转换。可自托管但非必须。
- ACL4SSR 同时提供规则模板（`ACL4SSR_Online.ini` 系列），是模板参考的标杆。

### 3.5 Cloudflare Worker 方案（psub / WorkerVless2sub）

- 免费、可私有化、国内可直连（worker 域名）；worker 可做「节点脱敏中转」（把真实 IP/密码替换成随机值再转交公共后端，转换后再还原，防止公共后端偷节点）。
- 缺点：worker 环境有 CPU/请求限制；本质仍是依赖公共后端或自建后端的轻量反代；无复杂模板能力。**可作为本项目后续的「外网访问层」参考，不作为核心路线。**

### 3.6 竞品对比结论

| 维度 | subconverter | SubConverter-Extended | Sub-Store | 本项目（自研） |
|------|:---:|:---:|:---:|:---:|
| 协议支持广度 | ★★★★★ | ★★★★（Mihomo 系） | ★★★★ | ★★★★（起步） |
| OpenClash 深度定制（命名契约） | ★★★（靠模板） | ★★★★ | ★★★ | ★★★★★（核心卖点） |
| 多订阅聚合 | ✅ `\|` 合并 | ✅ | ✅ | ✅ |
| 节点过滤/重命名 | ✅ 正则 | ✅ | ✅ 可视化 | ✅ 正则+规则化配置 |
| Web UI | ❌（需另配） | ✅ 仪表盘 | ✅ | ✅（自研轻量 UI） |
| 部署成本 | 极低（单二进制） | 低 | 中（Node） | 低（容器化） |
| 内存占用 | ~20MB | ~30MB | ~100MB+ | 低（Go/轻量方案） |
| 长期维护协议 | 人工 | 跟随内核 | 社区 | **复用内核解析器** |

**结论**：不重复造轮子——**协议解析层直接复用 Mihomo 内核解析能力**（Go 生态可嵌入 mihomo 的 parser，或借鉴 SubConverter-Extended 的 proxy-provider 输出策略）；自研重点放在**模板/规则/命名契约的深度定制 + 轻量 Web 管理 + OpenClash 无缝集成**。

## 4. 用户场景与痛点分析

### 4.1 用户环境事实（来自运维记录）

| 环境 | 事实 |
|------|------|
| 路由器 | 192.168.10.1，ImmortalWrt，OpenClash v0.47.x，Mihomo Dev 内核，fake-ip 模式 |
| 订阅 | 机场订阅被聚合为「订阅聚合.yaml」，节点名含 emoji 国旗 + 中文描述 + `\|` 分隔（如 `🇯🇵 AWS日本01 \| 电信移动联通推荐`） |
| 自定义规则 | `/etc/openclash/custom/openclash_custom_rules.list`，策略目标必须与订阅名称逐字符匹配（emoji/空格/`\|` 一个不能差），改后需重启 OpenClash |
| NAS | 192.168.10.10，OMV + mergerfs，Docker Compose 标准流程，**内存仅 3.8Gi，禁大内存批处理** |
| 代理出站 | OpenClash mixed-port 7893 显式代理（带认证），Clash API 9090 |
| 部署铁律 | 全容器化（Docker Compose），不宿主机裸跑；更新走 compose 标准流程 |

### 4.2 核心痛点（按优先级）

1. **P0 — 命名契约不可控**：公共转换模板/机场原生订阅生成的策略组名、节点名与自定义规则文件对不上，规则经常失效。每次机场改节点名，规则就要手工同步。
2. **P0 — 节点信息经第三方转换服务**：订阅 URL 含机场凭证，公共转换服务能看到全部节点内容（泄露风险 + 服务不可控/限流/跑路）。
3. **P1 — 多订阅聚合 + 规范化命名**：当前靠手工维护「订阅聚合.yaml」；希望多机场自动合并、去重、按统一规范重命名（如固定 emoji 前缀 + 地区 + 序号），让自定义规则长期稳定。
4. **P1 — 规则/策略组维护成本高**：希望转换模板即规则源（模板里定义域名组、节点组），改模板 = 改全屋分流，不依赖 OpenClash 里零散的手工规则。
5. **P2 — 协议支持演进**：机场上新协议（AnyTLS 等）时，公共后端往往滞后；自建需跟上。
6. **P2 — 故障排查困难**：订阅更新失败时（UA 限制、订阅源被墙、模板地址失效）需要可观测性（日志、健康检查、转换预览）。

### 4.3 典型使用场景

- **场景 A（日常）**：机场更新节点 → OpenClash 定时（如每天 4:00）更新订阅 → 访问 NAS 转换服务 → 生成符合命名契约的新配置 → 自定义规则无需改动。
- **场景 B（换机场/加机场）**：新增机场订阅 → Web 界面加入聚合列表 → 转换服务自动合并、按规范重命名 → OpenClash 更新订阅即生效。
- **场景 C（规则调整）**：要新增「AI 走香港节点组」→ 修改模板中的域名组/节点组 → OpenClash 更新订阅生效（或热更新 rule-provider）。
- **场景 D（排障）**：订阅更新失败 → Web 界面查看转换日志（哪个订阅源拉取失败/UA 被拒/模板解析错误）→ 一键重试。

## 5. 功能需求（FR）

### 5.1 核心转换功能（P0）

| 编号 | 需求 | 说明 |
|------|------|------|
| FR-1.1 | 多格式输入解析 | SS(SIP002)、SSR、VMess、VLESS、Trojan、Hysteria2、TUIC、AnyTLS、Socks5/HTTP、Clash YAML、Base64 订阅、SIP008 |
| FR-1.2 | 多订阅聚合 | 多个 URL 以配置方式合并（等价 `\|` 语义），自动去重（按 server+port+uuid 指纹） |
| FR-1.3 | 目标格式输出 | Clash/Mihomo YAML（primary）；预留 Surge/QuanX 等输出为远期 |
| FR-1.4 | 节点过滤 | 按关键字/正则 include / exclude（如过滤 `Traffic`、`GB`、`Expire` 等机场流量节点） |
| FR-1.5 | 节点重命名 | 正则替换 + 规范化命名规则（emoji 国旗映射、地区提取、序号追加、`\| 描述` 后缀模板），**保证与用户自定义规则命名契约对齐** |
| FR-1.6 | 自定义策略组 | 按地区/用途自动分组（`🇭🇰 香港节点`、`🚀 自动选择`…），组类型 select/url-test/fallback/load-balance 可配；组名可精确指定 |

## 7. 技术选型建议

### 7.1 方案对比

| 维度 | 方案 A：Go（复用 mihomo parser） | 方案 B：C++（fork subconverter） | 方案 C：Node.js（仿 Sub-Store） | 方案 D：Python |
|------|------|------|------|------|
| 协议解析 | ★★★★★（直接 import mihomo 解析逻辑） | ★★★★（人工维护，已滞后） | ★★★（第三方库） | ★★ |
| 开发效率 | ★★★★ | ★★ | ★★★★★ | ★★★★ |
| 内存/资源 | ★★★★（~30-60MB） | ★★★★★（~20MB） | ★★★（~100MB+） | ★★★ |
| 模板生态兼容 | ★★★（需自实现 ini 解析） | ★★★★★（原生） | ★★★ | ★★★ |
| 部署（单二进制/Docker） | ★★★★★ | ★★★★★ | ★★★★ | ★★★ |
| 长期维护成本 | 低（跟随内核） | 高 | 中 | 中 |

### 7.2 推荐：方案 A（Go，复用 Mihomo 内核解析能力）+ 关键组件选型

1. **语言/框架**：Go 1.22+（单二进制、低内存、容器友好、与 Mihomo 生态同源）。
2. **协议解析**：内嵌 [MetaCubeX/mihomo](https://github.com/MetaCubeX/mihomo) 的 `adapter/outbound` 解析器（parseLink）——协议支持自动跟随 Mihomo 更新；或抽其 `constant`/`config` 包。
3. **HTTP 服务**：标准库 `net/http`（或 gin，轻量即可）。
4. **YAML 处理**：`gopkg.in/yaml.v3`。
5. **模板引擎**：自研轻量模板（Go `text/template` + 预置规则组 DSL），同时兼容读取 subconverter `.ini` 模板（ACL4SSR 生态）作为输入适配层。
6. **正则/重命名**：标准库 regexp + 预置 emoji 国旗映射表（可配置）。
7. **存储**：无数据库，配置用 YAML 文件 + 内存缓存；日志滚动文件。
8. **前端**：静态单页（Vue3 或纯 HTML+JS，嵌入二进制 embed），不引入重型框架。
9. **Docker**：多阶段构建（golang:alpine → distroless/alpine），Compose 编排，healthcheck 用 `/healthz`。

> 备选路线（若评估后觉得自研解析成本高）：**Docker 化 subconverter（方案 B）作为 MVP 后端**，自研重点先放在「模板/命名契约/Web 管理」层，再逐步替换解析层。这个「先跑通、后替换」的策略风险最低。

## 8. 架构设计（草案）

### 8.1 模块划分

```
┌─────────────────────────────────────────────────┐
│                    Web 前端 (embed)               │
└──────────────────────┬──────────────────────────┘
┌──────────────────────▼──────────────────────────┐
│                HTTP API 层 (REST)                │
│  /sub (转换) /api/subscriptions /api/config      │
│  /api/contract-check /api/logs /healthz          │
└───────┬──────────────┬──────────────┬────────────┘
        │              │              │
┌───────▼───────┐ ┌────▼─────────┐ ┌─▼──────────────┐
│ 订阅源管理器   │ │ 转换引擎      │ │ 契约检查器      │
│ (拉取/UA/缓存) │ │ (解析→过滤→   │ │ (规则文件比对)  │
└───────┬───────┘ │  重命名→分组  │ └────────────────┘
        │         │  →模板合并→   │
┌───────▼───────┐ │  校验→输出)   │
│ 解析器适配层   │ └──────┬───────┘
│ (Mihomo parser)│        │
└───────┬───────┘ ┌──────▼──────────────┐
        │         │ 模板引擎             │
        └────────▶│ (内置模板 + ini 适配)│
                  └─────────────────────┘
```

### 8.2 关键数据流

```
OpenClash 定时更新
      │ GET /sub?target=clash&url=<聚合配置ID or 直接URL>
      ▼
订阅源管理器（缓存命中? 命中→直接返回）→ 逐源拉取（自定义 UA、超时、失败跳过）
      ▼
解析器适配层 → 节点列表（统一 Node 结构体）
      ▼
过滤（include/exclude 正则）→ 重命名（命名管线：emoji/地区/序号/描述）
      ▼
策略组构建（地区组 + 用途组）→ 规则注入（内置/rule-provider 引用）
      ▼
模板合并 → YAML 输出 → schema 校验（mihomo config 试加载）
      ▼
返回 YAML（Content-Type: text/yaml）+ 写入转换日志
```

### 8.3 与用户环境的部署拓扑

```
[ImmortalWrt 路由器 192.168.10.1]
  OpenClash (Mihomo 内核)
    ├─ 配置订阅 ──▶ http://192.168.10.10:25500/sub?target=clash&...
    └─ 自定义规则 /etc/openclash/custom/openclash_custom_rules.list

[NAS 192.168.10.10 / OMV / Docker Compose]
  openclash-sub-converter (本服务, 端口 25500 内网)
    ├─ 数据卷: ./config (订阅源/模板/规则配置), ./logs
    └─ 出站拉取: 直连机场订阅；被墙源可配置走 OpenClash 7893 显式代理
```

### 8.4 命名契约引擎设计要点

1. **命名管线**（可配置顺序）：emoji 映射（地区→国旗）→ 地区提取（HK/JP/SG/… 或中文）→ 名称清洗（去机场广告词）→ 序号/描述组装 → 输出 `🇭🇰 香港节点01 | 描述`。
2. **契约规则文件**：独立 YAML（如 `contract.yaml`），声明「自定义规则文件将引用的组名/节点名模板」。
3. **校验输出**：生成配置后，读取（或由用户上传）`openclash_custom_rules.list`，比对所有 policy 引用，输出三类结果：✅ 命中 / ⚠️ 缺失（规则引用了不存在的名字）/ ℹ️ 未引用（配置里有但规则没用）。
4. **dry-run 模式**：机场改名后先出报告再应用，避免全屋断网。

## 10. 风险与挑战

| 风险 | 等级 | 缓解 |
|------|:---:|------|
| 协议解析维护成本（新协议/参数演进） | 高 | 复用 Mihomo 内核解析器；输出前用内核 config 校验试加载 |

| 命名契约改动的连锁影响（全屋断网） | 中 | dry-run 报告先行；输出确定性；契约校验拦截 |
| OpenClash 版本/内核差异导致配置不兼容 | 中 | 以用户实际环境（Mihomo Dev 内核）为准做回归测试；输出最小必要字段 |
| NAS 资源约束（3.8Gi 内存） | 中 | Go 单二进制 + 无数据库 + 内存缓存上限控制；部署前实测 |
| YAML 生成正确性（转义/引号/中文/emoji） | 中 | 生成后用 mihomo 配置加载校验（测试套件）；emoji 与中文必须原样保留 |
| 机场订阅凭证安全（配置落盘） | 中 | env 注入 + 文件权限 + 日志脱敏 |
